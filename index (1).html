Problemática identificada

Los aprendices de ADSO de primer trimestre pierden avances de código, sobrescriben el trabajo de sus compañeros y entregan los proyectos por USB o correo, porque no comprenden el flujo de control de versiones. En el aula se observa temor a la consola y a "dañar" el repositorio, commits sin mensaje claro y repositorios sin README.

Intencionalidad pedagógica

Reforzar un aprendizaje y remediar una situación desfavorable: que el aprendiz pierda el miedo a Git practicando en un entorno guiado, con ejemplos de su propio proyecto formativo.

Objetivo de aprendizaje

Al finalizar, el aprendiz aplica el flujo básico de Git (init, add, commit, push, pull) y la colaboración por ramas y pull requests en GitHub para versionar el proyecto formativo de su equipo.

MÓDULO 1

¿Qué es Git y por qué usarlo?

Git es un sistema de control de versiones distribuido: guarda "fotografías" (commits) del estado de tu proyecto para que puedas volver atrás, ver quién cambió qué y trabajar en paralelo con otras personas sin pisarse.

GitHub es una plataforma en la nube que aloja repositorios Git y agrega herramientas de colaboración: issues, pull requests, revisión de código y publicación de sitios (GitHub Pages).

Git ≠ GitHub

Git es la herramienta que instalas en tu computador. GitHub es el "lugar" en internet donde compartes tus repositorios. Puedes usar Git sin GitHub, pero no al revés.

Conceptos clave

  • Repositorio: carpeta del proyecto con su historial de cambios.
  • Commit: punto guardado con un mensaje que explica el cambio.
  • Rama (branch): línea de trabajo paralela para una funcionalidad.
  • Remoto: copia del repositorio en GitHub (origin).

Práctica 1 (10 min)

Instala Git desde git-scm.com/downloads y configura tu identidad:

git config --global user.name "Tu Nombre"
git config --global user.email "tu_correo@soy.sena.edu.co"
git --version   # comprueba la instalación

MÓDULO 2

El flujo local: las tres áreas de Git

Directorio de trabajoArchivos que editas
preparagit add
Área de preparación(staging) lo que irá en el commit
guardagit commit
Repositorio localHistorial de commits
compartegit push
GitHub (remoto)Copia en la nube
git init                 # convierte la carpeta en repositorio
git status               # ¿qué cambió?
git add index.html       # prepara un archivo (o: git add .)
git commit -m "feat: agrega página de inicio"
git log --oneline        # ver historial

Buenas prácticas de commit

  • Un commit = un cambio con sentido.
  • Mensaje en presente y claro: fix: corrige validación del login.
  • Haz git status antes de cada add.
  • No subas contraseñas ni la carpeta node_modules: usa .gitignore.

MÓDULO 3

GitHub y el trabajo en equipo

Cuando varias personas trabajan en el mismo proyecto, nadie edita directamente la rama main. Cada integrante crea su rama, sube sus cambios y propone integrarlos con un pull request (PR) que otro compañero revisa.

git clone https://github.com/equipo/proyecto.git
git switch -c feature/formulario-registro
# ... editas, add, commit ...
git push -u origin feature/formulario-registro
# En GitHub: Compare & pull request → revisión → Merge
git switch main
git pull                 # trae lo último del equipo

Roles sugeridos en el equipo

RolResponsabilidad
Líder de repositorioCrea el repo, protege main, invita colaboradores.
Desarrollador(a)Trabaja en su rama y abre PR.
Revisor(a)Comenta y aprueba el PR antes del merge.

Los roles rotan en cada sprint.

¿Y si hay conflicto?

Git marca las líneas con <<<<<<< y >>>>>>>. Conversa con tu compañero, deja la versión correcta, borra las marcas y haz un nuevo commit. ¡No es un error, es parte del trabajo en equipo!

MÓDULO 4 · RETO EN EQUIPO (3 personas)

Reto: "Nuestro proyecto, una sola versión"

Situación: su equipo debe entregar la primera versión del sitio web del proyecto formativo. Hasta ahora cada uno tiene archivos sueltos en su computador.

  1. El líder crea el repositorio en GitHub con README y .gitignore, e invita a los otros dos.

  2. Cada integrante clona el repositorio y crea su rama: feature/inicio, feature/contacto, feature/estilos.

  3. Cada uno hace al menos 3 commits con mensajes claros y sube su rama.

  4. Abren 3 pull requests; cada PR debe ser revisado y comentado por otro integrante antes del merge.

  5. Actualizan el README con el nombre del proyecto, integrantes y cómo ejecutarlo.

Lista de chequeo de la entrega

  • Repositorio público con README completo.
  • 3 ramas creadas, una por integrante.
  • Mínimo 9 commits con mensajes descriptivos.
  • 3 PR revisados y fusionados en main.
  • Sin archivos sensibles ni dependencias subidas.

Entrega

Copien el enlace del repositorio en la actividad de Territorium. El instructor revisará el historial con git log --graph.
